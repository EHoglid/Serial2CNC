01 / SERVER SETUP

One CNC computer. Browser access.

The Windows server installation runs three automatic services: Web hosts the browser interface, API routes requests, and Agent reads program files and sends them to the CNC.

Install on Windows

Use Windows 10/11 or Windows Server (x64), with administrator access. Create a local program folder, such as C:\CNCPrograms, before running setup.

  1. Download and install the MSI. Get the Windows x64 installer from GitHub Releases when a release is available. Run it and approve the administrator prompt. The self-contained package needs neither Visual Studio nor a separate .NET runtime.
  2. Configure and start the services. Open PowerShell as administrator and run: 
    & "$env:ProgramFiles\Serial2CNC\setup-services.ps1" -WorkingDirectory 'C:\CNCPrograms'

    Setup grants the Agent access to that folder, provisions the Web HTTPS certificate, and starts the services. The services run under separate, least-privilege virtual accounts, not LocalSystem.

  3. Trust the public certificate on browser computers. Verify the certificate thumbprint shown by setup through a trusted channel before importing the public certificate into each client's trusted root certificate store. 
    %ProgramData%\Serial2CNC\Serial2CNC-Web.cer

    Distribute only this public .cer file, never the private PFX. The default self-signed certificate lasts two years; renew it before expiry.

  4. Open the Web interface. Visit https://<CNC-computer-name>:62899. Use the computer name covered by the certificate, not its IP address. Do not bypass certificate warnings.
  5. Save settings, then transfer. Set the Agent's program folder and extension filter (for example, *.nc), configure the CNC connection, and review framing and delay under Transfer options. Save the settings, select a file from the server folder, put the CNC into its receive mode, and start the transfer. Monitor status and logs; use Cancel to stop an active send.

Trusted networks only. There is no application login. Setup opens Web HTTPS port 62899 to the local subnet; API 62901 and Agent 62904 stay on loopback. Do not expose these services to the public internet. Review existing firewall rules as well.

Before a release is available, download and unzip an artifact from a successful Windows MSI workflow run (GitHub sign-in required). Installers are unsigned; use trusted builds and compare the MSI's SHA-256 hash with the accompanying checksum.

For custom certificates, service accounts, network shares, upgrades, or building the MSI, see the full Windows setup guide. Do not install manual services alongside the MSI services.

02 / WPF DESKTOP

Send directly from Windows

The WPF application is standalone and separate from the server MSI. It reads local files and connects directly to the CNC or converter using your Windows account.

  1. Build the desktop application. On a Windows build computer with the .NET 10 SDK, get the source and publish: 
    git clone https://github.com/EHoglid/Serial2CNC.git
Set-Location .\Serial2CNC
dotnet publish .\Serial2CNC\Serial2CNC.csproj -c Release -r win-x64 --self-contained true -p:UseAppHost=true -o .\artifacts\desktop
  2. Launch the app. Open artifacts\desktop\Serial2CNC.exe. To use another Windows x64 computer, copy the entire desktop output folder, not just the EXE. No separate .NET runtime or Windows services are required.
  3. Choose the connection. Select TCP (USR-W610) or Serial / COM. Open Settings to enter the destination or serial parameters, delay between lines, and Okuma framing option.
  4. Select and send a program. Browse to the CNC file, check the program name if using Okuma framing, put the CNC into receive mode, and start the transfer. Keep the app open and monitor progress until it finishes.

Choose one sender per connection. The WPF app does not control the server Agent or share its saved settings. Avoid sending from the desktop and server to the same CNC at the same time.

03 / CNC CONNECTION

Match the receiving machine

Both interfaces use the same transfer engine. Choose the transport that matches your wiring and the CNC's receive settings.

Connection What to configure
TCP / USR-W610 Enter the converter's reachable IP address and listening TCP port. Configure its serial side to match the CNC. Enable TCP XON/XOFF only when the receiving setup passes these flow-control characters through.
Serial / COM Choose the COM port on the sending computer and match baud rate, parity, data bits, stop bits, and handshake to the CNC. A virtual COM port can also be used when provided by your converter software.

Files are sent as ASCII, one line at a time, with CRLF (\r\n) line endings. Check the CNC manual for supported program format, cabling, and receive procedure. A completed send is not confirmation that the CNC accepted or validated the program; verify it on the controller before use.

Device reference: USR-W610 serial-to-Wi-Fi/Ethernet converter.

04 / OKUMA FIRST & LAST ROW

What the framing option adds

Enable Okuma OSP7000L framing when the controller expects a program-name header and a closing percent marker. Serial2CNC wraps the file contents with two extra transmitted rows:

Row Sent text Purpose
First $PART01.MIL% Program-name header: a literal $, the resolved program name, then %.
Middle Your file's rows The existing program content, in its original order.
Last % Closing marker after the final file row.

How the program name is chosen

If you enter a program name, it is trimmed and converted to uppercase, then used as entered. Include .MIL yourself if needed; it is not added to a custom name. Leave the name blank to use the filename without its extension, followed by .MIL, in uppercase. For example, part01.nc becomes PART01.MIL.

Framing adds rows; it does not replace them. The source file is not modified. Existing headers or trailing % rows are not detected or removed, so enabling framing on an already framed file creates duplicate markers. Disable framing if the file already contains the required wrapper or if your controller uses a different format.

With framing disabled, only the file's rows are sent; the program-name field has no effect. ASCII encoding and CRLF line endings still apply.

05 / TRANSFER DELAY

A pause between lines, not characters

Delay between lines (ms) adds a fixed wait after sending each row, before sending the next one. It applies to TCP and Serial, including the Okuma header and closing marker when framing is enabled.

Send row 1→ 100 ms →Send row 2→ 100 ms →Last row
  • 0 ms: no extra software pause. Transfer speed still depends on the connection, serial baud rate, and flow control.
  • 100 ms: adds a tenth of a second between rows. There is no delay before the first row or after the final row.
  • Timing example: 102 transmitted rows (100 file rows plus 2 framing rows) have 101 gaps. At 100 ms, that adds about 10.1 seconds, on top of connection time, transmission time, and any flow-control waits.

A delay can give a slower controller time to process incoming lines. Use the machine's recommended value and increase it if the receiver loses data. It does not change baud rate, pace individual characters, or replace the correct handshake settings.

Delay and flow control do different jobs. A delay always waits the configured interval between rows. TCP XON/XOFF additionally pauses before sending a line after XOFF and resumes after XON; Serial uses the selected handshake mode. Either can make a transfer take longer than the delay calculation alone.
